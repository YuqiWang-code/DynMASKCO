# PyVRP 适配器第一次冒烟：**空转（no-op）**，已定位原因并修

- 日期：2026-10-18
- 类型：**开发诊断（不用于任何结论）**
- 代码：`scripts/admission/panel_replanner.py::PyVrpFeasibilityReplanner`
- 上游：[G2 基线盘点](2026-10-18_G2基线盘点.md)

## 1. 第一次结果：与控制臂**逐位相同**

```
[arm] day 0 ok PyVrpFeasibilityReplanner utility=1793.89 422.0s
{'utility': 1793.888119917363, 'revenue': 1840.0,
 'distance_km': 461.1188008263707, 'n_served': 94, 'energy_kwh': 708.4109541454583}
```

对照控制臂 day 0：`1793.888119917363 / 1840.0 / 461.1188 / 94` —— **完全相同（15 位小数）**。

逐位相同意味着 PyVRP 判定**从未拒绝过任何订单**，即适配器空转成了"不过滤"的控制臂。

## 2. 原因（两个，都是我的 bug）

1. **池子上限把判定短路了**：`--pyvrp-max-orders` 默认 60，而池子（已接受未派车 ∪ 候选）
   在到达密集时远超 60 ⇒ `_jointly_feasible` 直接 `return True`。
2. **`served_mask` 用法错误**（已修）：原写 `x not in served_mask`，
   而 `served_mask` 是**按节点索引的布尔数组**，应写 `not served_mask[x]`。
   否则"是否在数组里"这种检查永远为 False ⇒ 池子里混进了已服务订单。

## 3. 已做的修正

- `served_mask` 改成按索引取值（已上传）；
- 重跑参数改为 `--pyvrp-time-limit 0.3 --pyvrp-max-orders 200`，让判定真正生效；
- 单日成本估算：194 次判定 × 0.3 s ≈ 58 s，可接受。

## 4. 必须预先写下的风险（在结果出来之前）

把池子上限放开后，PyVRP 要在 0.3 s 内对 **~194 个客户 + 时间窗**给出"全部可服务"的解。
这类规模下 0.3 s 很可能**解不出全服务方案** ⇒ 适配器会**误拒**大量本来可行的订单，
表现为"收入暴跌"。若出现这种情况，**不能**读作"外部求解器不如规则"，
只能读作"我的适配器给了它不够的时间"，必须在记录里区分这两者。

## 5. 这不能证明什么

- 第一次的"逐位相同"**不**说明 PyVRP 与 SAA 等价，只说明判定被短路了。
- 也**不**说明外部基线不可能进严格在线协议——通道已经打通（[PyVRP 冒烟](2026-10-18_PyVRP冒烟.md) `PYVRP_SMOKE_OK`）。
