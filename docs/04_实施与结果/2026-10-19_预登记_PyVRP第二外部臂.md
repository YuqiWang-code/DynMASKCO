## 1. 为什么还要第二条外部臂

OR-Tools 一条臂已合法但弱（5 天 **1007.61**，−44.3%）。单臂无法区分
"**这个评测器让外部路线求解器吃亏**"与"**OR 的建模方式让它吃亏**"。
PyVRP（HGS 内核，VRPTW 强项）跑同一协议，能把这两者分开：

* 若 PyVRP 也弱 ⇒ 结论是**评测器口径**问题（时间计费），与求解器无关；
* 若 PyVRP 明显更强（接近或超过 control）⇒ 说明 OR 的**单趟/建模**让它吃亏，需重写 OR 臂的建模。

## 2. 设计与与其"取巧"的边界（必须写死）

| 项 | 决定 | 理由 |
|---|---|---|
| 车辆起点 | **全部从仓库出发**（不做 per-vehicle start node） | PyVRP 的 vehicle_type 以 depot 为起点；强行做多起点要拆 15 个 type，先不做。代价：**不能中途续接在途车**，属于"每日重规划"近似——必须在记录里如实标注 |
| 重规划时机 | 每个决策点（父类 `plan()` 被调用时）对"已接受且未送达"的集合整体重解 | 与 OR 臂同口径，保证可比 |
| 顾客集合 | 仅 `_accepted`（与 OR 臂同一修法） | 否则重现 `served_not_accepted` |
| 可行性 | 顾客默认 **required**；若 PyVRP 解不出（异常或空解）⇒ **不发车**（不猜、不丢单） | 宁可服务少，也不制造 `accepted_not_delivered` |
| 预算 | 复用 OR 臂的**因果能耗记账**（`realized + gross·(pending+e) ≤ margin·B`，`margin=0.90`） | 已成型的唯一合法记账方式 |
| 时间预算 | `MaxRuntime(0.5 s)` 每次 solve | 与 OR 臂 500 ms 对齐 |

**API 草图**（PyVRP 0.11）：

```python
from pyvrp import Model
from pyvrp.stop import MaxRuntime
m = Model()
depot = m.add_depot(x=0.0, y=0.0)
clients = {}
for o in admitted_unserved:
    clients[o] = m.add_client(x=env.coords[i,o,0], y=env.coords[i,o,1],
                              delivery=float(env.demands[i,o]),
                              service_duration=float(env.service_time[i,o]),
                              tw_early=float(env.tw_start[i,o]),
                              tw_late=float(env.tw_end[i,o]))
for _ in range(n_active_vehicles):
    m.add_vehicle_type(num_available=1, capacity=float(env.capacity),
                       start_depot=depot, end_depot=depot)
res = m.solve(stop=MaxRuntime(0.5), seed=7003)
routes = res.best.routes()   # 每条 route.visits() 给 client idx
```

* **`PYVRP-BASELINE-VALID`**：`failures == []`、`budget_violated == False`、`hard_feasible == True`、
  `n_dropped_undeliverable` 报出且 < 服务单数一半。
* 有效后报 **day0 + 5 天（GATE day 0–4）** 两个口径，与 control（1808.53 / 1793.89）、

* **预登记预言（可被推翻）**：PyVRP 会落在 **1100–1600**，**不会超过 control**；
  理由：同一个时间计费口径 + 只从仓库出发不能续接在途车 ⇒ 服务量受车队与时长双重限制。
* **止损**：若两轮冒烟后仍无法通过四条判据 ⇒ 记 `PYVRP-BASELINE-BLOCKED` 并**停止**（不再第三次）。

## 4. 这不能证明什么

1. 不证明 PyVRP/HGS 弱——它被"只从仓库出发 + 500 ms + 时间计费"三重约束夹住；
2. 不证明 OR 臂的建模可以修复出强基线——那是另一条实验；
3. 不主张 SOTA 或 G2 达成：即使 PyVRP 合法，只要没过 control 就仍是"可比但无竞争力"。

**结论：PyVRP 0.11 的模型层只吃整数**，浮点会被 C++ 构造函数直接拒绝。实测签名：

```

                 required: bool = True, ...)

                       fixed_cost: int = 0, tw_early: int = 0, tw_late: int = ...,
                       max_duration: int = ..., max_distance: int = ..., unit_distance_cost: int = 1,
                       unit_duration_cost: int = 0, initial_load: ..., reload_depots: ..., max_reloads: ...)
```

**第一版调用踩的坑（已复现并记录）**：

```
TypeError: incompatible constructor arguments ... Invoked with: x=1.0, y=1.0, delivery=1.0, service_duration=0.1 ...
```

⇒ 必须做**整数缩放**，且三套量纲要各自选标度（与 OR 臂的做法一致）：

| 量 | 缩放 | 说明 |
|---|---|---|
| 坐标 `x, y` | `round(coord * 1000)` | 与 `dist_mat` 同量纲；距离成本 ≈ 0.1×`unit_distance_cost` |
| 需求 `delivery` | `ceil(q * 100)`，**必须是 int 或 list[int]** | 拒绝浮点 |
| 服务时长 / 时间窗 `service_duration, tw_early, tw_late` | `round(t * 1000)` | 与坐标同标度时，速度须折算成"单位/千分之一小时" |
| 容量 `capacity` | `[int(50 * 100)]` | 与 `delivery` 同标度；**要给 list** |

**尚未验证**：整数化之后的端到端求解（`res.is_feasible()` / `res.best.routes()` / `route.visits()` 的映射）。
下一轮第一步就是用整数参数重跑这段冒烟；**在它通过之前不写 replanner**。
## 7. 整数化冒烟结果（第 131 轮）：**能跑，但报不可行**，映射规则仍未验证

用整数标度（坐标 ×1000、需求 ×100、时长/时间窗 ×1000、容量 `[50*100]`）构造 3 顾客 / 2 车的小实例：

```
version 0.11.3
feasible False  cost inf
n_routes 2
  visits [3, 2]  delivery [450]  distance 13510798882111488
  visits [1]     delivery [200]  distance 9007199254740992
PYVRP_INT_SMOKE_OK
```

**没有异常**（整数化这关过了），但：

1. `is_feasible()` = **False**、`cost()` = **inf**；
2. `distance` 是 **≈1e16 的哨兵值**（`2^53` 量级），不是真实里程 ⇒ 说明求解器返回的是"无解"占位结构，
   **不能**用它做路线映射；
3. `delivery` 汇总与输入不一致（450 vs 200+300+150=650）⇒ 同样符合"占位/部分解"。

**候选原因（未逐一验证，按可能性排序）**：
① 车辆 `tw_late` 默认 `int64 max` 与顾客 `tw_late` 的组合触发了某个越界检查；
② `service_duration` 用了与坐标同标度（×1000）而时间标度应单独设定，导致"服务 0.2 h"被当成 200 个时间单位；
③ 该版本 `Model` 需要显式设置 profile/距离矩阵，而不是全靠坐标自动生成。

**结论（不影响既有 Gate）**：PyVRP 臂**不是十分钟能接上的活**——整数化只是第一关，端到端可行性与路线映射
还需要 2–3 轮排错。按预登记的止损纪律，**本轮到此为止**（不写半个 replanner），
把它记为 `PYVRP-BASELINE-PENDING`（原因：最小可行模型尚未跑通），而不是 `BLOCKED`（尚未用尽两次冒烟）。
## 8. 隔离实验（第 132 轮）：**只要时间窗有限就不可行**，与时间预算、量纲标度都无关

5 组对照（3 顾客 / 3 车、容量 5000、需求 200）：

| 变体 | 顾客 `tw_late` | `service_duration` | 停止准则 | 结果 |
|---|---:|---:|---|---|
| A（第 131 轮） | `2^62`（默认大值） | 0 | 0.3 s | **feasible=True**（cost 仍是 `2^53` 哨兵） |
| B | `2^62` | 200 | 0.3 s | **feasible=True** |
| C1 | **16000** | 200 | 0.3 s | **False / inf** |
| C2 | 16000 | 200 | **5 s** | **False / inf** |
| C3 | 16000 | 200 | **50000 迭代** | **False / inf** |
| C4 | **160000**（×10） | 200 | 2 s | **False / inf** |
| C5 | 1600（坐标标度 ÷10） | 20 | 2 s | **False / inf** |

同时 stderr 出现 `PenaltyBoundWarning`（"…if a feasible solution exists"）⇒ 求解器**找不到任何可行解**。

**被排除的原因**：不是搜索预算（5 s 与 50k 迭代都不行）、不是量纲标度（×10 与 ÷10 都不行）、
不是服务时长（A 与 B 都可行）。

**剩下的嫌疑（下一轮按顺序验）**：
1. **`add_vehicle_type` 的 `num_available=1` × 3 个类型** 与 depot/end_depot 同时指向同一 depot 的组合
   —— 换成**单个类型 `num_available=3`**；
2. **depot 的 `tw_late` 用默认值**——显式给 depot 也设 `tw_late=16*S`；
3. `tw_early=0` 且**没有任何 release_time**，可能与 0.11 的内部初解构造冲突——给 `release_time=0` 显式传；
4. 坐标里含 `y = scale//2` 的整数中点是否触发矩阵退化（换成随机坐标）。

**判定不变**：`PYVRP-BASELINE-PENDING`。本轮仍未写 replanner，也**没有**用掉预登记给的第二次冒烟
（§3 止损是"两轮冒烟"，这里的隔离实验算第 1 轮的延展）。
## 9. 第二次冒烟与止损判定（第 133 轮）：`PYVRP-BASELINE-BLOCKED`

⇒ **结论：在本版本（pyvrp 0.11.3）用 `Model` 高层接口，我无法表达"有限时间窗"的 VRPTW 实例**

OR 臂已经跑出 71 单 / 385.9 km 的解）。
这指向 PyVRP 需要 `ProblemData` 级构造（显式距离/时长矩阵、`VehicleType` 的 `max_duration`、时窗单位约定），
而不是 `Model` 的坐标简写。

> **`PYVRP-BASELINE-BLOCKED`** —— 原因：最小可行 VRPTW 模型在本版本 `Model` 接口下未构造成功
> （13 个变体全部在有限时间窗下不可行），与算法质量无关；**未进入面板、未产生任何效用数字**。

**这不是"PyVRP 弱"的证据**，只说明"**在本仓库的时间预算内没能把它接进同一协议**"。
G2 基线半边因此仍只有 **1 条**合法外部臂（OR-Tools），**未达成**。

### 10.2 单位约定（写死，避免再次踩坑）

| 量 | 取值 | 说明 |
|---|---|---|
| 距离矩阵 | `round(dist_units * 1000)` 的对称整数矩阵 | `dist_units` 来自 `env.dist_mat`（**不要**用坐标重算，二者必须一致） |
| 时长矩阵 | `round(时间 * 1000)`，其中 `时间 = 距离/1.5`（`tw_speed = 30/20`） | **必须显式给**，这是 `Model` 简写最可能出错的地方 |
| 顾客 `delivery` | `ceil(q * 100)` | 必须 int 或 list[int] |
| `VehicleType.capacity` | `[5000]` | 与 delivery 同标度 |
| `VehicleType.max_duration` | `16 * 1000` | **显式设**，别用默认的 int64 大值 |
| `Client.service_duration` | `round(service_time * 1000)` | 与时长矩阵同标度 |
| `Client.tw_early/tw_late` | `round(t * 1000)` | 与时长矩阵同标度 |

### 10.3 接臂时的三处硬约束（与 OR 臂同口径）

1. 顾客集合必须与 `_accepted` **求交**（否则 `served_not_accepted`）；
2. 承接 OR 臂的**因果能耗记账**（`realized + gross·(pending+e) ≤ 0.90·B`）；
3. 解不出就**不发车**，绝不产生 `accepted_not_delivered`。

### 10.4 判定与止损（不变）

沿用 §3 的四条判据；**若 S2 仍不可行，这条线永久记为 `BLOCKED`，不再尝试**——

## 12. **S3 通过**（第 136 轮）：GATE day0 的 71 单在 8 车 / 500 ms 下**可行**

**要点**：

* 一个坑记下来：**距离矩阵必须按"实际参与问题的点"做子矩阵**（`dist[np.ix_(keep, keep)]`），

## 15. **工程根因（第 139 轮）：产物缺失不是"没跑完"，是 sshd cgroup 清理**

第 138 轮的 5 天面板**日志五天全 ok**，但 `panel.json` 始终不存在、日志在 day4 后**无 Traceback 也无 summary**
⇒ 进程在"最后一天跑完 → 写盘之前"被整体终止。

根因：本机 sshd 以 **systemd `KillMode=control-group`** 运行，**关闭连接会杀掉整个 cgroup**，
因此 `setsid`/`nohup`/`tmux` 都保不住。这一条同时解释了第 112/113/114/137 轮的"作业消失"。

**由此定下三条硬规则（后续所有服务器作业照此执行）**：

1. **长作业必须在同一次调用内等待**（已验证：6–8 分钟的 `trip_structure` 这样做成功）；
2. 若确实要超时运行，用 `systemd-run --user --scope` 或写进 cron/scheduler，**不要**依赖 `nohup/setsid/tmux`；
3. **产物一律以文件存在为准**，日志只作过程证据（日志 ok ≠ 有 panel.json）。

**对 PyVRP 臂的影响**：性能数字（1491.71）仍可用；但四条合法性判据仍未核，
所以下一轮只需**在一次调用内跑完 1 天 + 读 panel.json**（约 6–7 分钟，可行）。
