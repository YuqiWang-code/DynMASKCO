## 1. 第一版跑了什么

为了缩短等待时间，先用 `--train-days 20` 跑了一次（`/tmp/headroom2.log`）：

```

  "headroom_reglobal_pct": 42.19 }
```

## 2. 为什么这组数不能用

**只有 2 辆车、10 单**——而正常一天是 15 辆车、约 104 单、493 km。
原因是 `build_history(train_ds)` 只有 20 天样本，SAA 的场景采样质量崩了，导致它几乎不派车。
因此这组 9.37% / 42.19% 是**在一个退化的基线上**算出来的，**不能**用来回答"真实路线有多少余量"。

这正是我在记录模板里反复要求的那条的实例：**先检查基线是否可信，再解释数字**。

## 3. 已做的修正（进行中）

同一脚本改跑 `--train-days 200`（完整校准集），并加了分阶段进度打印：

```
train_ds ready (0.1s, 200 days)   ← 生成本身很快（0.1 s / 20 天）
history ready
running env day 0 ...             ← 真正的时间成本在这里，约 320–400 s/天
env done
```

**关键认识**：这套审计的耗时瓶颈**不是**数据生成，而是 `env.run`（一天约 320–400 s，且当前 9 个面板在抢 CPU）。
以后凡是要跑 `env.run` 的脚本，都要**先打印阶段进度**，否则日志空白会被误判为卡死。

## 4. 这不能证明什么

- 9.37%（每车 2-opt）与 42.19%（全局重排）**都不是**真实余量，因为基线只有 10 单。
- 两项余量都**不检查时间窗**；reglobal 还改变了车辆-订单分配，属乐观上界。
- 因此本记录**不**支持"里程有大量余量"或"里程无余量"中的任何一方。

## 5. 下一步

1. 等 `--train-days 200` 版本给出**与基准日（104 单 / 493 km）可比**的余量；
2. 若可实现余量（2-opt + 时间窗可行性筛选）> 5%，则把 GPU 训练的打分器接进闭环作为新臂；
3. 若可实现余量 < 2%，则把"冻结协议下 G4 不可达"写成决定性负结果，主线收口到 I-1 + I-3。
