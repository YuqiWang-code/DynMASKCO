# G1-L8 环境层重放：**FAIL（顺序依赖）** —— 并列到达的数组位置会改变服务集合

- 日期：2026-10-18
- 类型：**泄漏发现（实测）**：`FAIL_ORDER_DEPENDENT`
- 脚本：`scripts/tests/test_no_future_l8_env.py`（新增 `--days 1 --n-orders 60 --burst-rate 0.6`）
- 上游：[G1 现状 7/8](2026-10-18_G1现状_7of8.md)、[L8 定义收紧](2026-10-18_G1缺口_泄漏检查5到8.md) §5

## 1. 实验

按 §5 收紧后的 L8 定义：只对 **`reveal_time` 相同的并列订单**做数组位置互换，
在**完整 `StrictOnlineEnv` + `SaaReplanner`** 上重放，比较"被接受订单的属性签名集合"。
本次并列订单 **8 个槽位**被互换（burst 0.6、60 单、1 天）。

## 2. 结果

```
days=1 orders=60  swapped_slots_in_day0=8
accepted sizes base : [47]
accepted sizes perm : [48]
days with differing accepted set: [(0, 47, 48)]
discriminating: True
verdict: FAIL_ORDER_DEPENDENT
```

**同一批订单、同一 reveal 时刻、同一随机种子，仅把并列订单在数组里的位置互换，
服务集合从 47 单变成 48 单。**

## 3. 这意味着什么

1. **这是一个真实的顺序依赖（L8 泄漏）**：策略/环境对"同时到达"的订单有**隐式优先级**，
   而该优先级来自**数组下标**，不是任何被声明的规则。
2. **它对结果有实质影响**：服务集合差 1 单（47 vs 48）。按 `REV` 口径，1 单 ≈ 10–30 收入。
   在多天统计上足以污染 ±0.5% 量级的结论——而我们全部的 A/B 差值都在 1% 上下。
3. **可被利用**：任何知道"数据是按某顺序排列"的参与者都可以通过重排输入来影响结果。
   严格在线协议本应让并列到达**语义上无序**。

## 4. 对 G1 的判定（必须如实改）

| 类 | 之前 | 现在 |
|---|---|---|
| L1–L7 | ✅ | ✅ |
| **L8** | 🟡 数据层+接拒层通过、环境层未做 | **❌ FAIL**（环境层顺序依赖，实测） |

⇒ **`G1 = 7/8`，且 L8 由"未实现"变为"已测且失败"。**
这**不是**"更接近达成"，而是**发现了一个必须修的协议缺陷**。

## 5. 修法（已登记，未实施）

1. **协议层**：把"同一 `reveal_time` 的订单"定义为**集合**，决策必须**与它们在数组中的位置无关**
   （例如：先按 `(temp_class, demand, x, y)` 规范化排序，再逐单决策；或一次性对整组做集合决策）。
2. **基准层**：生成器输出前对并列组做**确定性规范化排序**（键与 id 无关），
   使"数组位置"成为订单属性的函数而非常量下标。
3. **验证层**：把本次重放固化为 `verify_no_future.py` 的一项（当前是独立脚本），
   任何新数据集必须过这一项。
4. **重跑影响**：修好后所有面板需重跑一次；在修好之前，**既有结论的相对比较仍然有效
   （所有臂共享同一顺序固定），但绝对值的可迁移性再降一档**，这一点必须写进论文的限制章节。

## 6. 这不能证明什么

- 不证明既有结论错：所有臂都在同一"顺序固定"下评测，配对差仍然可比。
- 不证明 L8 在其他数据上一定失败：本次 burst=0.6 是人为加密并列比；真实数据集当前并列数=0
  （[§6 实测](2026-10-18_G1缺口_泄漏检查5到8.md)），因此**现有六集不受此缺陷影响** ——
  只有将来引入 burst 的数据集才会。
- 但正因为 §6 显示现有数据**没有并列**，L8 此前一直"不可判别"；本实验是**人为造并列**才暴露了缺陷。

## 7. 修法尝试（同日）：规范化并列排序**不足以**修复

已在 `strict_online_env.py` 加可选开关 `canonical_tie_order`（默认 `False`，保证既有结果逐位可复现），
在两处对并列到达做属性规范化排序：

1. `on_reveal` 的 `_vis`；
2. `_plan_and_commit` 的 `visible_ids`。

排序键为 `(reveal_time, temp_class, demand, x, y)`，与数组下标无关。

**重跑结果：仍然 FAIL。**

```
accepted sizes base : [47]
accepted sizes perm : [48]
verdict: FAIL_ORDER_DEPENDENT
```

## 8. 残余依赖定位（结论）

规范化输入顺序**不足以**消除依赖 ⇒ 泄漏不在"环境喂给策略的顺序"，
而在**策略内部把节点映射成临时 id 的方式**：
`SaaReplanner._sync_id_map` / `_map_node`（`scenario_saa.py:299–315`）按**首次出现顺序**
建立 `node → 临时 id` 映射，而 SAA 内部的比较/排序（如 `argmin` 打平、场景采样）会受临时 id 影响。
换句话说：**即使输入是无序集合，内部编号仍然编码了顺序。**

⇒ 真正的修法需要让 SAA 的**内部编号也与属性挂钩**（例如按 `(class, demand, x, y)` 排序后编号），
或让所有打平比较都按属性键裁决。**这是一处更深的改动，本轮未做。**

## 9. 对 G1 的最终判定（本轮）

- **`G1 = 7/8`，L8 = `FAIL`（实测，且修法一次尝试失败）**。
- 既有六集并列数为 0 ⇒ 历史上不受影响；**burst 数据集必须修好 L8 才能用**。
- 新增的可选开关 `canonical_tie_order` 默认关闭，**不改变任何既有结果**；
  它作为"部分修法"保留，供下一步在 `_sync_id_map` 层继续。
