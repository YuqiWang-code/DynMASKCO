## 1. 前两次为什么 BLOCKED（根因，逐条对着代码）

| # | 现象 | 根因（代码级） |
|---|---|---|
| 1 | `served_not_accepted` | `baselines/ortools_rolling_horizon.py::ORToolsReplanner.plan` 的 `remaining = 可见未服务 − reserved`，**没有与 `_accepted` 求交** ⇒ OR 会服务从未被接单层接受的订单 |
| 2 | 能耗 **1186.8 / 预算 710.65** | 接单判据只记 `Σ e_lower ≤ B`，**完全不含冷机固定开销**（第 99 轮实测：固定开销 = 预算的 **32.0%**）⇒ OR 真把单跑完时必然超预算 |
| 3 | 早先的 `TypeError` / `pickup exceeds capacity` | 需求 `astype(int)` 截断、容量浮点等工程 bug（已在上一轮修掉） |

## 2. 本轮的两处最小修法（只改接缝，不动 OR 求解器本体）

* **修法 1（顾客集合求交）**：`ORToolsSaaReplanner.plan` 把 `visible_ids` 过滤成
  `{i ∈ visible_ids : i ∈ self._accepted}` 后再交给 OR；空集时**不发车**（不回退到父类 SAA 规划，
  否则会把未接单的可见单排进路线）。
* **修法 2（因果能耗记账接单）**：接单判据由"`Σ e_lower ≤ B`"改为
  `realized + pending + e(o) ≤ 0.98·B`，其中
  `realized` = 当前所有车辆 `coldchain_state.cumulative_energy_kwh` 之和（**已实现**能耗，含固定开销）；
  `pending` = 已接但未送达订单的 `e_lower` 之和。
  三个量都是因果的（只读当前车辆状态与已接受集合，不读未来）。
* **修法 3（丢单回收）**：OR 允许丢单（disjunction）。`plan()` 求解后把"已接但既未送达、
  也不在任何车 suffix/committed 上"的订单在**日内**退回 `_rejected`，并计数
  `n_dropped_undeliverable`，避免终局 `accepted_not_delivered`。

## 3. 判定（这是**基线有效性**判定，不是优越性判定）

**`ORT-BASELINE-VALID`** 需同时满足（1 天冒烟 + 5 天面板都要满足）：

1. 每天 `failures == []`（无 `served_not_accepted` / `accepted_not_delivered` / `commitment_violation` / `duplicate_service`）；
2. 每天 `budget_violated == False` 且 `energy_kwh ≤ 710.6548`；
3. 每天 `hard_feasible == True`；
4. `n_dropped_undeliverable` 报出来（不设阈值，但必须 < 服务单数的一半，否则该臂等于"大量撤回接单"，须在记录里说明）。

否则记 **`ORT-BASELINE-BLOCKED-v3`**，附**逐条失败标签**，停止该方向（不再第四次尝试）。

## 4. 若有效：它对既有结论的影响（先写清楚，避免事后解释）

* 它是**外部基线**（OR-Tools 是工业级 CP-SAT 路由求解器），因此它进入 12 条基线表后，
  "最强基线"的候选集合从 {登记静态 λ} 扩大为 {登记静态 λ, OR-Tools 路线}。
* **若它的 utility 显著高于 1815.82**：则本项目此前所有"领先"表述必须重新以它为分母核算，
  且 **G4 的门槛要对着它算**（这意味着 G4 更难，不是更容易）。**不许**因为它是"外部臂"而把它排除在最强基线之外。
* **若它低于静态 λ**：则"接拒层已榨干、路线层被结构关死"的两条结论获得**独立外部证据**支持。
* 预登记预言（可被推翻）：**它的 utility 会落在 1500–2000 区间，且不会显著超过登记静态 λ**。
  理由：接单层与静态 λ 同源（同一 λ 过滤器），路线层只有 4–5 辆车可派且容量锁死；
  第 99 轮的趟结构诊断显示控制臂的 461 km 已被 4 条链分摊，OR 的改进空间主要在链内顺序，
  而链内顺序已被 2-opt 测试为精确零。

## 5. 这不能证明什么

1. 不证明 OR-Tools 在**其他协议**（可撤销承诺、允许延迟）下不更强。
2. 不证明"外部基线一条都进不来"——恰恰相反，本轮就是把"进不来"变成"进来但不变强"或"进来且更强"。
3. 不主张 SOTA；不主张机制创新；不因为臂名带 OR-Tools 就把它当"强基线"或"弱基线"，只看数字。
4. `energy_margin = 0.98` 是**安全余量**而非调参旋钮；若因它丢单导致 utility 下降，如实记录不得回调。
